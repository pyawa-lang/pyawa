## 1. 定位

Pyawa 是用 Rust 从零实现的、语义对标 CPython 3.14 的 Python 方言。

它**不是**"更快的 Python"。两个真正的卖点：

1. **类型检查真正生效的 Python**——渐进类型 + 在标注/未标注边界插入运行期检查并归责。
   这件事 CPython + mypy 在原理上做不到：注解被擦除，且没有可插入检查的执行引擎。
2. **像 Lua 一样易嵌入的 Python**——稳定 C ABI、多实例隔离、无全局状态、沙箱原生。

**非目标**（写下来是为了防止范围蔓延）：

- 不提速
- 不运行 C 扩展
- 不自带数据/查询 DSL（由下游宿主构建）
- 不承诺 free-threading

## 2. 语义基准与兼容契约

基准：CPython **3.14**。级别：**语义级**（含元类、描述符、生成器帧、异常栈、`inspect`、import 副作用）。

兼容承诺的**可执行判据**见 `PLAN-milestones.md`（`MS-`）；下面这句是它的定性表述：

> **差异只允许出现在「能力是否存在」这一维，且必须表现为看起来像真实机器的错误；
> 不允许出现在「写法 / 句柄 / 类型」这一维。**

直接推论：

- `fd` 仍然是 `int`；`select.select([fd])`、`os.dup2`、`socket.fileno()` 必须照常工作
- 3.14 的注解语义（延迟求值）在范围内
- 受限 provider 不得引入新的句柄类型或新的编程写法
- **两种失败必须分得清**：接口槽位**未实现** ⇒ 调用时返回"未实现"错误
  （这是关于"该嵌入提供了什么"的事实）；宿主**已实现但拒绝** ⇒ 必须表现为真实机器的错误
  （`PermissionError`/`FileNotFoundError`）。前者不是权限语义，后者才是

### 2.1 后缀即模式开关（兼容契约的执行机制）

> 层次先说清：**Pyawa 是 Python 的一个方言**（唯一的那个）；`.py` 与 `.pyawa`
> 是**同一个方言内的两种模式**，不是两个方言。二者是**子集关系**：`.py ⊂ .pyawa`。

| 后缀 | 模式 | 新增特性 |
|---|---|---|
| `.py` | 纯 Python 模式（CPython 3.14 语义） | **一律报 `SyntaxError`** |
| `.pyawa` | 扩展模式（纯语义 ＋ 新增特性） | 启用 |

四条性质：

- **模式是逐编译单元的属性，不随 import 传染。** `.py` 与 `.pyawa` 可共存于同一项目、
  互相导入；被导入文件的模式由**它自己的后缀**决定
- **重名即错误**：忽略后缀后不得重名（`foo.py` 与 `foo.pyawa` 不能处于同一可导入位置）。
  项目级共存、模块级互斥——迁移是**整文件替换**，不是并存同名
- **`Lib/` 全是 `.py`** ⇒ 标准库天然隔离于扩展，不需要额外纪律
- **先例**：TypeScript 的 `.ts`/`.tsx`（JSX 只在 `.tsx` 合法）——同一机制，已被大规模验证

**这个概念是承载的**（若把它当成"两个方言"，下面四条会全部崩掉）：

- **一份语法、一份语义规范、一份实现**——模式只是编译参数，不存在两套文法/两套语义
- **一套工具链**——LSP、formatter、debugger、profiler 都只有一个，模式是参数
- **新增特性必须是纯增量**：不得改变任何现有 Python 构造的语义。
  若某个特性需要改语义，它就不能以"扩展"形式存在（那会同时破坏 `.py` 的纯净与 `.pyawa ⊃ .py`）
- **可机械验证**：两模式的**差异只能来自扩展模式叠加的效果**（校验／边界检查，`TS-5`）——
  纯 Python 模式下的标注**不产生任何检查**；既有构造的**读法**在两种模式下不变

**`.py` 保证的落地点**：`.py` 模式下扩展语法必须报 `SyntaxError`。这是可测的——
把 `Lib/` 与纯 Python 语料全部以 `.py` 模式编译，断言行为与 CPython 一致。

**扩展特性：规则索引**（只指向、不重述——一处真相）：

| 要素 | 出处 |
|---|---|
| 准入：**纯增量**，不改变既有构造的语义 | `DESIGN.md` §13 的 `12.` |
| 模式是编译器的**显式输入** | `BC-14` |
| 纯 Python 模式下，**任何扩展语法必须报 `SyntaxError`**；**禁止"先解析再忽略"** | `BC-15` |
| 不走新语法的扩展（借用**既有合法构造**表达）在 `.py` 下**合法**且**不产生检查** | `TS-5` |
| 检查**只在扩展模式**；档位是编译期参数 | `TS-5`、`TS-31` |
| 扩展模式**没有参照实现** ⇒ 扩展语料目前可以为空 | `MS-13` ③ |
| **多语句 `lambda` body**：扩展模式下 `( 语句… 末表达式 )` 合法；`.py` 下报 `SyntaxError` | `BC-62` |
| **可空标注 `T?`**：等价于 `T | None`，只用在标注位置；`.py` 下报 `SyntaxError` | `TS-46` |

**实现路径（不需要改 `Lib/`）**：`_bootstrap_external` 用
`sys.path_hooks.extend([FileFinder.path_hook(*supported_loaders)])` **追加**默认钩子
（已核实：第 1560–1561 行），`zipimport` 就是这么抢到 `sys.path_hooks[0]` 的。
因此 Pyawa 在启动引导里 `sys.path_hooks.insert(0, ...)` 一个 `FileFinder` 子类
（`importlib.machinery.FileFinder` 是纯 Python、可继承），在其 loader details 里加
`.pyawa` 并实现重名检查即可。**`Lib/importlib/` 一字不动。**

**字节码产物：`.pyac`——Pyawa 自有格式。`.py` 与 `.pyawa` 编译出的产物都用这个后缀**
（各自对应自己的源文件），与 CPython 的 `.pyc` 无关且不兼容。因此上游那套
`cache_from_source`／`__pycache__`／`source_from_cache` 的关系**与 Pyawa 无关**，
编译与缓存由 Pyawa 自己的 loader 负责。

⚠ **待定：`.pyac` 的命名与陈旧判定。** 判据只有一条——
**源文件被重命名（`foo.py` → `foo.pyawa`）后，旧产物不得被误命中**（并存歧义已由重名规则排除）。
如何命名、如何判陈旧（mtime／size／内容 hash／把源文件名写进产物）、格式布局，都还没定（§13 第 15 项）。

**已知差异**：按 `.py` 后缀识别文件的第三方工具（`pkgutil` 扫描、`importlib.resources`、
coverage、部分 linter）看不见 `.pyawa`。

## 3. 总体架构

```
宿主程序
   │  稳定 C ABI（仅嵌入，不做扩展模块）
   ▼
Pyawa 实例 (State)   ← 一切可变状态的唯一宿主
   ├── VM：字节码解释器 + 帧栈 + sys.monitoring 事件点
   ├── 对象模型：对象头 + 引用计数 + 循环回收
   ├── 类型系统：编译期校验器 + 边界强制转换
   └── 能力层：唯一的 I/O 出口（依赖倒置）
          │  能力 provider（默认 ＝ 真实机器）
          ▼
     真实机器 / 宿主资源
```

四条**架构不变量**（违反其中任何一条都需要推翻重来）：

1. **不存在未注入的 I/O**——所有外部世界访问经能力层
2. **不存在全局可变状态**——所有状态挂在实例上（`lua_State` 模型）
3. **panic 不跨 FFI**——每个 C ABI 入口 `catch_unwind`
4. **跨线程的能力调用不碰 VM 对象**——只传裸数据与 OS 句柄（见 §7.2）

## 4. 对象模型与内存

- **对象头**：type 指针 + 引用计数 + flags（预留无 GIL 所需位）+ 变长尾
- **引用计数非原子**——"先 GIL"决策的直接后果；换来的是一整类内存序问题消失
  （注意不变量 4：这条的成立**依赖**于没有跨线程的 VM 对象访问）
- **必须有循环回收器**：`gc.collect()`、`gc.get_objects()`、`weakref`、`__del__` 触发时机都是语义的一部分
- **禁用 `Rc`**：处理不了循环，也不提供 `sys.getrefcount` / `id()` 要求的可观测性

⚠ **未决**：immortal 对象策略（CPython 3.12+ 把 `None`/`True`/`False`/小整数做成 immortal）。
`sys.getrefcount` 的返回值是否要逐值对齐 CPython——对齐则实现被锁死，不对齐则兼容宣称有缺口。

---

## 5. 执行模型

- 栈式字节码 VM；编译期完成作用域分析、常量折叠、名称槽位解析
- 生成器/协程用可挂起帧实现；`async`/`await` 与生成器共用帧机制
- 异常用 3.11+ 的**异常表**模型（zero-cost exceptions），需支持异常组（`except*`）
- `sys.monitoring` 事件点**必须在主循环里预留**（调试器与 profiler 是已确认的工具链需求）
- GIL：非原子引用计数 + 实例内单线程；`threading` 映射到宿主线程并保持 GIL 语义
- 栈回溯、帧对象（`frame`）、`sys._getframe` 属于语义级兼容范围

⚠ **未决**：`_interpreters`（3.12+ 子解释器）是否在范围内。多实例隔离已经覆盖了大部分动机，
子解释器的主要增量是"进程内隔离 + 共享不可变对象"，可以推迟。

## 6. 类型系统

**渐进性是核心机制，不是可选功能。** 安全度是**程序级属性**：由标注覆盖率决定。
语言既不强制安全，也不阻止安全；它的义务是让**安全端真实成立**。

⚠ **生效范围（模式）**：**校验**只在**扩展模式**（`.pyawa`）下启用；纯 Python 模式下的标注
**照常合法且照常保留**（`REQUIREMENTS.md` 类型生效范围／标注的可用性两行）——二者**不校验**，
但**不等于不许标注**。跨模式调用是否被检查，由**被调用方**是否已标注决定
（`SPEC-type-system.md` `TS-5`）。

**模型**：标注决定严格度，不做推断。

- 未标注 ⇒ `Any`，与一切相容，不做校验（程序**选择**了此处不安全）
- 标注 ⇒ 编译期校验（程序**选择**了此处安全）
- **边界强制转换 + 归责**：未标注代码调用标注函数时，VM 在入口插入运行期检查，
  失败时**归责给调用方**，而不是让错误在深处炸掉

**必须满足的两个性质**（否则"可以选择安全"就是空话）：

1. **渐进保证（gradual guarantee）**——Siek / Vitousek / Cimini / Boyland,
   *Refined Criteria for Gradual Typing* (2015)：增删标注不得改变程序行为（类型错误除外）。
   这是安全谱可信的前提：若加一个标注就可能改变运行时行为，"选择安全"本身就是危险动作，没人会走。
2. **边界归责（negative blame）**——Wadler / Findler, *Well-Typed Programs Can't Be Blamed* (2009)：
   全标注代码不得为源自未标注代码的错误背锅。这正是 Pyawa 区别于 mypy 之处：
   注解不只在编译期提示，还在边界上真实生效。

**cast 深度是安全谱的一部分**（浅层 / 深层），不是降级 fallback。深层检查贵
（transient gradual typing 一类工作正是为压这个成本），因此它应当是程序可选的档位，
而不是默认全开或整体放弃。

**产品含义**：既然安全档位是程序级选择，宿主就应当能**检查并强制**它——
例如编译产物携带"标注覆盖率 ＋ 严格档位"报告，宿主据此决定是否加载该脚本。

⚠ **关键未决**（重要性与"是否强制"无关）：

1. **边界检查粒度**：每个参数？每个返回值？容器内部检查到第几层？
   粒度越深，越接近契约式设计，也越贵。
2. **归责错误的形态**：新异常类型（如 `TypeBoundaryError`）还是沿用 `TypeError`？
   前者更清晰，后者更兼容。
3. **与 `Any` 的相容规则**：consistency relation 需要精确定义，
   否则"边界强制转换"会在第一个 `Any` 处退化成擦除式。
4. **性能**：边界检查落在最热路径上。性能不是目标，但需要实测一个可接受的上限。

⚠ **结构性局限**：因为"完全不推断"，存量无标注代码完全不受保护。
边界检查能补强"未标注 → 标注"的方向，但补不了"全程未标注"的代码。
这是"`Lib/` 逐字同步 + 不推断"两个决策的必然代价，应当在对外描述里说清楚。

## 7. 能力层（沙箱原生）

**前提：脚本来自用户/玩家，不可信，也不需要可信；运行时在服务端；脚本不能逃逸。**
沙箱因此不是"一个模式"，而是 VM 与宿主之间的**职责划分**：

| 域 | 归属 | 内容 |
|---|---|---|
| **VM 自治域**（不可下放） | VM | 语言语义；运行时自身的内存安全；**不可逃逸**；资源记账；可中断 |
| **宿主控制面**（策略） | 宿主 | 授予哪些能力；资源预算；暴露哪些宿主对象；生命周期 |
| **脚本** | — | 完全不可信，不参与任何信任决策 |

四条由此推出的原则：

1. **权威在 provider，判定在 VM。** provider 只提供"权威"（如"这个目录"）；
   路径规范化、句柄校验、预算核算由 VM 执行。这样一个简陋甚至有 bug 的 provider
   **也无法导致逃逸**——逃逸防护不是每个 provider 作者的义务。
2. **只有一个接口面：宿主实现它。** 没有"策略配置面"与"实现面"之分——
   provider 就是宿主实现的那个接口（POSIX 形状的细接口）。宿主实现一遍即可，
   而不是在运行期逐次审批；若需要逐次审批，VM 就不被需要了。
3. **不可逃逸与可中断是 VM 的内建不变量**，不是宿主可选功能。
   服务端跑不可信脚本时，"脚本卡死整个服务"与"脚本读到 `/etc/shadow`"必须是同一级别的
   **默认不可能**，而不是"宿主记得配一下"。
4. **未实现的接口槽位在调用时返回"未实现"错误。** 不是创建期拒绝，也不是权限语义——
   Pyawa 里**没有"权限"这个概念**，只有"实现了"与"未实现"。
   宿主若要拒绝某个操作，是它自己在实现里返回 `PermissionError`（见 §9）。
5. **VM 没有"平台"概念。** 它不认识操作系统，只认识这层接口。
   沙箱不是"一个可以关掉的功能"，而是 **VM 与外部世界之间的那层边界本身**：
   当它的实现恰好是真实机器时，VM 就自动获得真实环境操作能力——
   **等效于没有沙箱，但沙箱客观存在**。
   ⚠ 这条必须**机械强制**：VM 核心 crate 不得依赖 `std::fs`/`std::net`/libc，
   不得出现 `#[cfg(target_os)]`——用 CI 检查，不靠自觉（同 §3 不变量 2 的处理方式）。

**宿主不是"选择能力控制面"，而是直接实现沙箱所要求的接口。** 这是彻底的依赖倒置：

- 沙箱**定义**它需要的接口，宿主**实现**它。没有配置项、没有权限清单、没有策略 schema——
  宿主的策略就写在它的实现里（不想给文件系统，就把 `open` 实现成返回 `PermissionError`）
- **接口按能力域切分**：宿主实现哪些域 ＝ 提供哪些能力；**未实现的槽位在调用时返回"未实现"错误**。
  于是"宿主控制它想控制的"是自然结果，而不是一条需要遵守的约定
- **独立运行时自动注入真实机器实现**（同一接口的另一个实现）。所以"纯 Python 程序都能跑"
  在独立运行时下无条件成立；嵌入时是"在宿主已实现的域内"成立。两者都与 §2 表述一致
- **实现是一次性的，不是逐次审批**：宿主实现一遍 `fs` 域（约二十个函数），
  此后 VM 自主跑脚本。若宿主需要逐个调用审批，那 VM 就不被需要了——
  粒度问题因此自动消失，不需要额外"保持粗粒度"的纪律

先例：这**就是 WASI 的模型**——运行时定义 imports，宿主提供实现，
独立运行时提供基于真实操作系统的实现。

### 7.1 形状：能力对象面 + VM 侧 POSIX 适配层

provider 接口是**能力对象面**（无全局命名空间，凭据就是能力对象）。
但程序看到的必须是 POSIX 语义，因此 VM 侧维护一层 POSIX 适配：

```
os.open("/a/b")  →  VM 路径解析（相对"根能力"）  →  provider: Dir.open("b")
                 ←  能力对象   →  VM 分配 fd 槽位  →  返回 int
os.read(fd, n)   →  VM 查实例能力表  →  能力对象.read(n)
```

**关键洞察：POSIX 的 `fd` 本来就是"进程内文件表的下标"。** 所以"能力对象面 provider + 实例内能力表"
不是妥协，而是对 POSIX 语义的忠实实现。由此：

- `fd` 永远是 `int`；`select.select([fd])`、`os.dup2`、`socket.fileno()` 全部照常工作（满足 §2）
- 沙箱边界 ＝ **根能力**：受限 provider 交出一个代表子树/受限资源的目录能力，
  绝对路径看起来仍然绝对，只是相对于这个根解析（WASI preopen / chroot 的同一思路）
- 残余的 ambient authority：cwd、uid、`os.getpid()`、`time.time()` 不是能力，
  只能由 provider 提供**受控值/常量**来模拟

### 7.2 阻塞与可中断：c 方案 + 一条硬不变量

已选 **c：能力调用走独立线程 + 取消令牌**。它与"先 GIL + 非原子引用计数"（§4、§5）能共存，
**但依赖不变量 4**：

> **跨线程的能力调用只允许传递裸数据与 OS 句柄，不得传递或触碰任何 VM 对象。**

否则多线程会读到 VM 堆 ⇒ 引用计数必须原子化 ⇒ 实际等于 free-threading（已明确不承诺）。

推论：能力必须分成两类。

| 类别 | 例子 | 线程模型 | 可中断 |
|---|---|---|---|
| **可异步化**：只涉及裸数据 / OS 句柄 | 文件、socket、时钟、随机、进程 | 送 worker 线程 | ✅ |
| **不可异步化**：需要 VM 对象 | 宿主对象方法、触碰脚本对象的能力 | 留在 VM 线程 | ❌ 同步窗口 |

并且：VM 线程等待能力结果时**必须使用可取消的等待**（带超时 / 轮询），
不能无限阻塞——否则宿主既中断不了 I/O，也中断不了等待 I/O 的脚本。

⚠ **未决**：宿主自定义能力属于哪一类，必须由宿主注册时声明；声明错了就是数据竞争。

### 7.3 能力域清单

每域需声明三件事：**语义契约**、**对应模块**、**可否异步化**。

| 能力域 | 对应 C 层模块 |
|---|---|
| 文件系统 | `posix`、`_io` |
| 网络 | `_socket`、`select` |
| 进程 | `posix`（fork/exec）、`_signal` |
| 时钟 | `time` |
| 随机 | `_random`、`os.urandom` |
| 环境与身份 | `posix`（`getenv`/`getpid`/`getuid`） |
| 终端 | `termios`、`readline`、`_curses` |
| 区域与编码 | `_locale`、`_codecs*`、`unicodedata` |
| 进程内共享 | `_thread`、`mmap`、`_posixshmem` |

### 7.4 ⚠ 根能力的边界情形（受限 provider 的安全核心）

- **符号链接逃逸**：路径解析必须防 `..` 与符号链接跳出根能力——这是受限 provider 的头号安全点
- **cwd**：`os.chdir` 是实例状态，却参与路径解析，必须与根能力一起定义
- **绝对路径 + 根能力 ＝ chroot 语义**；`os.getcwd()` 需要伪造一个看起来合法的值
- `/proc`、`/dev`、`/sys` 在受限 provider 下不存在 → 必须表现为 `FileNotFoundError`（符合 §2）

## 8. 嵌入接口（C ABI）

只做嵌入，**不做扩展模块**。已确认的接口形态：

### 8.1 线格式：栈式（Lua 风格）

所有宿主函数与能力函数都通过**虚拟栈**收发参数与返回值。
栈是**稳定的 ABI 线格式**：不随语言演进变化，不需要为新增参数形态改 ABI。

### 8.2 类型元数据：声明签名 + 生成 `.pyi`

栈是线格式，**签名是类型元数据**，两者互补而非冲突：

- 宿主注册函数/类型时提供签名 → 编译期据此校验调用，并可生成 `.pyi` 存根（LSP 可见）
- 生成的 stub 内部就是从栈上按签名取参数
- 这是 Lua 之类嵌入引擎**没有**的能力：宿主 API 进入类型系统

### 8.3 宿主对象：注册为真实类型

- 宿主声明一个类（方法表 + 属性 + 签名）→ Pyawa 创建**真实的类型对象**
- 因此 `isinstance`、属性访问、特殊方法、**边界强制转换**（§6）对宿主对象全部生效
- 生命周期：**引用计数交给脚本**；宿主提供析构回调，并必须提供 **`traverse` 回调**参与循环回收
  （宿主对象 ↔ 脚本对象互相持有时的唯一解法，等同 CPython 的 `tp_traverse`/`tp_clear`）
- **桥接即能力**：宿主对象是逃逸的经典通道——暴露一个"方便"的对象可能等于开一个旁路。
  因此宿主对象/方法的暴露必须走与 §7 **同一套授权模型**，而不是另立一套"注册即授予"

### 8.4 需要暴露的面

- 实例生命周期：创建 / 销毁 / 中断
- **宿主必须提供沙箱所要求的接口实现**（见 §7）：`create` 接收宿主实现的**能力域 vtable**；
  未实现的槽位在调用时返回"未实现"错误。独立运行时提供同一接口的真实机器实现，不经过宿主
- 执行：编译、执行字符串/文件/字节码
- 宿主函数注入、值转换、错误传递（异常绝不跨边界逃逸）
- 能力 provider 注册（按能力域替换）
- 宿主类型注册（含析构与 `traverse` 回调）

⚠ **未决**：

- **ABI 版本策略**：嵌入 API ＋ provider 契约 ＋ 宿主对象契约，三者都要在第一个公开版本定死
- **宿主类型是否允许被脚本继承**（CPython 用 `Py_TPFLAGS_BASETYPE` 表达此意图）；
  若允许，虚方法分派与 `super()` 需要宿主参与
- **签名元数据的存放位置**（嵌入二进制？伴随文件？运行时注册？）——影响跨模块类型检查

## 9. 标准库策略

**`Lib/` 逐字同步上游，无须修改。** CPython 的 **C 实现层**（`_io`、`posix`、`_sre`…）
用 Rust 重写，且它就是能力接口的实现——依赖倒置与标准库策略是同一件事，
CPython 自身就有这条接缝。

这条要求的精确含义：

> **"无须修改" = 文件逐字来自上游且能正确工作。** 不要求行为与 CPython 逐位相同——
> 那是由 C 层承担的**语言层语义契约**。

**"C 兼容"必须拆成三种，但只做其中两种，第三种连"兼容"都不需要：**

| 种类 | 内容 | 做不做 |
|---|---|---|
| **C-API / ABI** | `PyObject`/`PyTypeObject` 布局、`tp_*` 槽、`Py_DECREF` 宏、CPython 头文件、能加载 C 扩展 | **不做**（早已明确：加载 C 扩展的不算） |
| **C 模块的 Python 层行为** | `_io.open`、`posix.stat`、`_socket.socket` 等**从 Python 看到的** API 与语义 | **必须做**（纯 Python `Lib/` 依赖它） |
| **数据格式**（字节码产物、`marshal`、code object 序列化） | 字节流长什么样 | **不要求跨实现兼容**——Pyawa 用自有格式 `.pyac`（§2.1） |

第三条为什么不要求兼容：**Pyawa 的编译产物根本就是自有格式**——`.pyac`，`.py` 与 `.pyawa` 共用，
既不读也不写 CPython 的 `.pyc`，与它无关也不兼容。上游 `_bootstrap_external.py` 里
`marshal.dumps/loads` 与 `_imp.pyc_magic_number_token` 那条 `.pyc` 路径
（第 224／511／528／539 行）**不在 Pyawa 的路径上**：编译与缓存由 Pyawa 自己的 loader 负责。

由此：

- **不需要实现 CPython 的 C-API，对象模型可以完全按 Pyawa 自己的设计来**
  （与 §4"对象头自己设计、不用 `Rc`"一致）
- 那些**把 C-API 概念暴露到 Python 层**的模块——`ctypes`/`_ctypes`、`_testcapi`、
  `_testbuffer`、`xxlimited*`——走"未实现"路径（导入即报未实现），
  计入实现缺口清单，**不是兼容性破坏**
- `marshal` 只需**存在**（`_bootstrap_external.py` 第 30 行会 import 它）并保证
  **Python 层行为**（支持的类型集、往返、错误行为）——它是公开模块，纯 Python 库会直接用；
  其 code object 序列化路径不在 Pyawa 的关键路径上
- 连带效果：CPython 生成的 `__pycache__/*.pyc` 与 Pyawa 完全无关（不读不写）；
  只发行 `.pyc` 而不带 `.py` 的包在 Pyawa 上不可用（罕见，列为不支持）

三条推论：

- **可机械校验**：CI 比对本仓库 `Lib/` 与上游 CPython 3.14.x 的**文件哈希**；
  任何差异必须出现在**显式例外清单**里并注明理由。这样"无须修改"就是一条会红会绿的性质，
  而不是一句口号（同 §3 不变量 2、§7 原则 5 的处理方式）
- **禁止本地给 `Lib/` 打补丁**：发现的 bug 只能通过 C 层修复或推给上游，
  否则例外清单会慢慢长成第二个分叉
- **署名与许可**：逐字同步意味着保留上游版权头，需随附 PSF LICENSE 与归属说明

### 零例外：缝吸收了字节码描述模块

`Lib/opcode.py` 与 `Lib/dis.py` 一度看似必须例外，其实**它们就是同一个缝**：
纯 Python 包装 + C 内核（已核实：`opcode.py` 第 13–16 行 `import _opcode` /
`from _opcode_metadata import ...`；`dis.py` 第 22 行 `from _opcode import get_executor`）。

因此：**`opcode.py` / `dis.py` 逐字同步且不改**，而 `_opcode` / `_opcode_metadata`
作为 C 层由 Pyawa 提供——**暴露 Pyawa 维护的指令表**（基线为 CPython 3.14 的指令名与编号，
另有 Pyawa 专有指令，见 `SPEC-bytecode.md` 的 `BC-30`／`BC-31`）。
于是 `dis` 会正确反汇编 Pyawa 的字节码，而文件内容一字未动。**例外清单为空：纯 Python 标准库 100% 逐字同步。**

`_opcode` / `_opcode_metadata` 需要导出的符号可以从那两个文件的 import 直接读出来，不用猜
（完整清单见 `SPEC-bytecode.md` §2）：

- `_opcode`：`stack_effect`、`get_executor`、`has_arg`／`has_const`／`has_name`／`has_jump`／
  `has_free`／`has_local`／`has_exc`、`get_intrinsic1_descs`／`get_intrinsic2_descs`／
  `get_special_method_names`／`get_nb_ops`
- `_opcode_metadata`：`opmap`、`_specializations`、`_specialized_opmap`、`HAVE_ARGUMENT`、
  `MIN_INSTRUMENTED_OPCODE`

⚠ **这是有代价的，别当成捡来的便宜。** 因为这两个文件**在 import 时就会索引具体名字**：

- **`opmap` 必须含 27 个指定指令名**——`EXTENDED_ARG`、`COMPARE_OP` 由 `opcode.py` 直接索引；
  另 25 个由 `dis.py` 索引，其中含超指令 `LOAD_FAST_LOAD_FAST` 与 3.14 新增的
  `LOAD_SMALL_INT`、`LOAD_COMMON_CONSTANT`
- **code object 必须暴露 17 个 `co_*` 属性 ＋ `co_positions()`／`co_lines()`／
  `_varname_from_oparg()`**，否则 `dis` 与 traceback 的列信息都不成立

结论：**"自有字节码"的自由度只在于编号与编码，不在于指令名与 code object 的可见属性。**

⚠ 同类还有一处（**同一个缝的第三次**）：`Lib/importlib/_bootstrap_external.py` 逐字同步 ⇒
它第 30 行会 `import marshal`，所以 `marshal` 必须存在；但 Pyawa 的编译产物是自有的
**`.pyac`**（§2.1），**不走**该文件的 `.pyc` 缓存路径。格式无需跨实现兼容。

### 效果一致性的精确边界

承诺：**纯 Python 库不改动、直接可用、使用效果完全一致。** 这条**自动成立**——
只要"语言语义一致"＋"C 模块的 Python 层行为一致"，任何纯 Python 库就只是跑在这套语义上的代码，
不存在第三条依赖。唯一需要划清的是**观测实现**的那一类：

| 库的类型 | 能否直接用 | 效果 |
|---|---|---|
| 纯 Python，不观测实现 | ✅ 逐字可用 | **完全一致** |
| 纯 Python，**观测实现** | ✅ 逐字可用 | **必然不同**——它在*测量*实现，而实现确实不同 |
| 涉及 C（C 扩展、C-API 概念模块） | ❌ | 需移植；C 扩展不在范围内则不可用 |

第二类不是移植问题，而是逻辑上不可能：**不能既不是 CPython、又报告自己是 CPython**。
已知的"实现观测面"：`sys.implementation`、`sys.version`、`platform.*`、`sysconfig`、
`dis`/`opcode`、`sys.getrefcount`、`gc` 统计。

**关键推论（这是载荷决策，不是细节）：** 第三方纯 Python 库大量使用
`if platform.python_implementation() == "CPython"` 或
`if sys.implementation.name == "cpython"` 来选择 C 加速路径。因此
**`sys.implementation.name` 必须报 `pyawa`**：库会据此走它**自己写好的纯 Python 回退路径**——
效果一致，只是路径不同。若谎报 `cpython`，库会去加载不存在的 C 模块然后失败。
**生态里现存的"非 CPython 回退路径"正是这句承诺能成立的原因。**

**生态边界的实话**：因此"有生态"的可用范围 ＝ **PyPI 上纯 Python 的那部分**。
numpy / pandas / lxml / cryptography 这类含 C 扩展的库，要么有人改写为纯 Python，
要么在 Pyawa 上不可用。这应当写进对外描述，避免过度承诺。

- 时间用 `CLOCK_MONOTONIC`；"整程"那行是**外部**计时（含 exec ＋ ld.so），与 `python3 -c pass` 同口径
- 内存读 `/proc/self/statm`（当前 RSS）与 `/proc/self/status` 的 `VmHWM`（峰值）；两侧都不 `import`

- **整程对比不是"同功能"对比**：本宿主没有 site／stdio 初始化、没有导入系统（`print` 要
  `fs` 域，尚未落地，`CM-26`）⇒ 只作量级参考，**别**读成"Pyawa 比 CPython 快 9 倍"
- 三次复跑的波动（同一提交）：引导 median 46–48 µs、整程 median 1.02–1.06 ms、峰值 3.28–3.40 MB
- 数值随 build profile 差一个数量级（debug 的引导 365 µs）⇒ **对外引用只用 release**
- 对 `§13-19` 的可用事实：单个空实例的常驻增量约 **0.7 MB**（release 2432→3120 KiB），
  跑一段最简脚本再涨约 0.3 MB；"是否拆容器专属 gc 链"仍**未定**，等有真实负载的实测再裁

`re`(`_sre`)、`_struct`、`_datetime`、`_json`、`_csv`、`_hashlib`、`select`、`_socket`、
`mmap`、`zlib`/`_lzma`/`_bz2`/`_zstd`、`_multibytecodec` + `_codecs_*`

**好消息**：`_decimal` 有纯 Python 备份 `_pydecimal.py`（6,402 行），可先移植它作为参考实现。

### ⚠ 移植附带的"环境权威审计"

`os`/`socket`/`subprocess`/`ctypes`/`multiprocessing`/`mmap` 等模块默认假定自己拥有环境权威，
必须逐个映射到 §7 的能力域接口上。宿主未实现某域时，`import os` 仍应成功，而操作在**调用时**
返回"未实现"错误；若宿主**已实现但拒绝**，则必须长得像真实机器的错误
（`PermissionError`/`FileNotFoundError`）。两者不能混用，否则破坏 §2 的兼容表述。
宿主对象桥接同理（§8.3）：它也是逃逸通道。

### ⚠ 独立子项目：Unicode

`encodings` 是 stdlib 里最大的一块（**32,612 行**），配合 `unicodedata`、`_multibytecodec`、
`_codecs_*`，覆盖大小写折叠、NFC/NFKC 规范化、双向文本。
⚠ **未决**：需钉死 3.14 对应的 **Unicode 版本与数据表来源**——这是一个独立的、可能数人月的工作量。

### 包管理：推迟（不急）

不自建安装器与 resolver。**但"推迟包管理" ≠ "可以忽略 site 语义"**：

- `Lib/site.py` 是纯 Python、逐字同步 ⇒ `sys.path` 构建、`site-packages` 扫描、`.pth` 处理
  **会按上游原样生效**，Pyawa 不需要为此额外做什么
- 于是用户路径自然成立：宿主或外部 `pip` 把纯 Python 包装到某目录，Pyawa 通过 `sys.path` 读到。
  这让"推迟"几乎零成本——**只要 import 与 site 语义正确，包管理就不必由 Pyawa 提供**
- 将来若要自建安装器，它是一个**独立工具**，不触碰 VM

|---|---|
| **范围** | 288k 行 stdlib + 113 个 C 模块 + 完整对象模型 + 类型检查器 + C ABI，是**数年量级** |
| **卖点被稀释** | 不推断 + 存量代码无标注 ⇒ 未标注代码完全不受保护；"Any 静默流过"仍是默认体验 |
| **c 方案与引用计数耦合** | 一旦跨线程传了 VM 对象，refcount 就必须原子化 ⇒ 等于 free-threading。不变量 4 是唯一的护栏 |
| **受限 provider 成本** | 契约要求模拟真实机器语义，写一个受限 provider ≈ 模拟一个操作系统；根能力逃逸是安全核心 |
| **归责检查开销** | 边界检查在热路径上，需实测可接受上限 |
| **兼容验收** | 判据已定（`PLAN-milestones.md`），但 **harness 尚无实现**——M6 之前"做完了没有"仍只能靠人工判断 |
| **子项目爆炸** | Unicode、`re`、`_decimal`、`asyncio`、`multiprocessing` 每一个都可能吞掉数月 |
