# CONSTRAINTS — 不变量与 CI 强制项

> 规范性文件 · 状态：v0
> 读者：实现 CI 检查的人，以及任何要动 VM 核心／能力接口／`Lib/` 的人
> **冲突时的优先级**：`REQUIREMENTS.md`（决策）> `SPEC-*.md`（执行细则）> `DESIGN.md`（架构论证）

规范用语：**必须** / **禁止**。硬约束编号 **`CX-n`**，测试编号 **`T-CX-n`**。

---

## 1. 范围与依赖

**规定**：那些**可以被机械检查**的不变量，以及每条**现在能否落地**。
本文件是这些约束的**唯一规范出处**——`tests/ci/` 只负责**实现**检查，各 crate 的 `README.md` 只负责声明
"本 crate 受哪几条约束"。

**不规定**：约束的**理由**（在 `DESIGN.md` §3／§7 与 `REQUIREMENTS.md` 后果 10）；
被引用条目的**内容**（`OM-`／`BC-`／`CP-` 各自在自己的规格里定义）。

| 依赖 | 用途 |
|---|---|
| `DESIGN.md` §3 | 四条架构不变量——本文件把它们变成检查项 |
| `DESIGN.md` §7 原则 5 | VM 核心无平台依赖 |
| `DESIGN.md` §2.1 | 模式开关与"扩展特性必须纯增量" |
| `DESIGN.md` §9 | `Lib/` 逐字同步与禁止本地打补丁 |
| `REQUIREMENTS.md` 后果 10 | 三条可 CI 强制的不变量 |
| `PLAN-milestones.md` §7 | `T-MS-1`／`T-MS-5`——与 `CX-1`／`CX-2` 同源，见 §4 |

## 2. 上游硬契约

### 3.1 静态检查的扫描范围

三条"扫代码"的约束，范围**必须**如下。范围是这些约束**定义的一部分**，不是实现细节——
因此**不另领编号**：

| 约束 | 扫哪里 | **不**扫哪里 |
|---|---|---|
| `CX-3`／`CX-6` | `crates/pyawa-core/src/` | 该 crate 的 `tests/` |
| `CX-4` | `crates/pyawa-core/src/` ＋ `crates/pyawa-capabilities/src/` ＋ `crates/pyawa-stdlib/src/` | `crates/pyawa-runtime/`（它**就是**平台依赖的集中点，`DESIGN.md` §7 原则 5）、各 crate 的 `tests/` |

- **理由**：这三条约束的是**随包发布的实现**；`tests/` 目录里的夹具代码不随包发布。
- **`pyawa-stdlib` 从第一个模块起就纳入 `CX-4`**：它自己的硬约束写着"**禁止**把 OS 与 libc
  直接拖进模块实现——外部世界一律经能力层"（`DESIGN.md` §3 不变量 1）；该 crate 的模块一旦
  自行 `use std::fs`，能力层就不再是唯一 I/O 出口。
- **内联测试不豁免**：`src/` 内的 `#[cfg(test)]` 代码**照扫**——为保持检查是纯文本扫描、不做 Rust 解析。
  若某段内联测试确实需要被禁的写法，正确做法是**改测试**（把夹具参数化），而不是给检查开豁免。
- **新增 crate 时必须复核本表**：新 crate 若属于"VM 核心或能力接口"一侧，**必须**加进来；
  若属于"真实机器实现"一侧（如 `pyawa-runtime`），**禁止**加进来。

## 4. 与 `PLAN-milestones.md` 的收敛

`CX-1`／`CX-2` 原先与 `T-MS-1`／`T-MS-5` 重复定义。按"一处真相"收敛如下：

- **约束与测试的定义**都在本文件（`CX-1`／`CX-2`、`T-CX-1`／`T-CX-2`）
- `PLAN-milestones.md` 的 M0 判据①／② **只引用** `CX-1`／`CX-2`
- `T-MS-1`／`T-MS-5` **已作废**——按 `SPEC-INDEX.md` §2，编号保留、不复用
- **唯一实现处**是 `tests/ci/`
