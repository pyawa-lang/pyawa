# 提交规则

> 提交不常发生，所以细则放这里；`AGENTS.md` 只留每次任务都要守的边界。

## 1. 一个提交只做一件事

- 一次提交对应一个逻辑改动；文档、代码、目录与格式清理**不混在同一次提交里**
- 提交时必须处于可验证状态：`cargo check --workspace` 通过，不留"中间坏状态"

## 2. 主题行格式

```
<类型>: <做了什么>
```

类型只有这几个（英文小写，冒号后一个空格）：

| 类型 | 用于 |
|---|---|
| `feat` | 新增功能（VM、对象模型、C 模块…） |
| `fix` | 修 bug |
| `docs` | 文档、规格、README、AGENTS.md |
| `chore` | 目录、构建、工具链等杂项 |
| `refactor` | 不改行为的重构 |
| `test` | 测试与对拍 harness |

- 主题行用中文写"做了什么"，动词开头，结尾不加句号
- 主题行必须能独立读懂这次改动的性质，不依赖正文

## 3. 正文只写"这次改了什么"

- **写**：改了哪些文件／模块、为什么、影响面；涉及的规格编号（如 `OM-21`、`BC-25`）
- **禁止写**：过程叙述（"先 ff 合并，又 reset 回来，最后重建"）、项目约定与规则、
  待办清单、对前一次提交的辩解
- **禁止把 commit 当公告栏或文档**：约定、流程、决策一律写进文档（见 `docs-rule.md`）。
  在 commit 里重复会产生第二个真相源，而且没人会去翻历史找约定

> 反面例子（本仓库真实发生过）：把「分支与合并约定」抄进提交说明里；
> 在提交说明里写「重建仓库基线」，把 git 操作过程昭告给所有后来者。

## 4. 提交前必查

- `cargo check --workspace` 通过
- **`python3 tests/ci/check.py` 全绿**——它是 `M0` 的判据（`CX-1`／`CX-2`），也是唯一会查
  "编号悬空／重复定义／路径不存在"的东西
- **这些检查必须当作"门"**：命令行**必须**用 `&&` 串联，让红灯**真的中断**提交；
  **禁止**用 `;` 或 `| tail` 之后照常提交——那样红灯只是打印出来，提交照旧
  （本仓库真实发生过：加粗包反引号的 ID 被算成第二次定义，红灯未中断，直接推上去了）
- `git status` 里没有意外内容：`target/`、`*.pyac` 已被 `.gitignore` 覆盖，不该进库的一个都不进；
  **出现不认识的未跟踪项（例如人类刚新建的目录）必须先停下问清，不得当作无关项跳过**
- 引用的规格编号真实存在（`OM-` / `BC-` / `CP-` / `AB-` …）
- 文档集状态变了，同步 `docs/SPEC-INDEX.md` §1 文档表的「状态」列

## 5. 提交到哪、怎么推

- 一律提交到 `dev`，**禁止直接提交到 `main`**（分支与合并规则见 `branch-rule.md`）
- 推送：`git push`（`dev` 已跟踪 `origin/dev`）；`origin = git@github.com:pyawa-lang/pyawa.git`
- **禁止 `push -f`**；推送前工作区必须干净、§4 的检查必须已通过
